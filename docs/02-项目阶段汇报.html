01 / 背景与痛点

原流程完成了打标，
但没有完成处置

圆准达派件电联经过语音平台识别后，只有 value=2 下入柜，其余标签一律按送货上门处理。客户的真实需求与末端动作之间仍有断点。

INPUT95 号电联
客户与快递员通话
→
TAG语音平台打标
Racking 1～8
→
value=2 → IN_STATION，允许入柜
其他值 → resetCheck，送货上门

指定地点被一刀切

客户说放门卫，原流程仍按普通上门，具体地点需求被丢弃。

→ 提取地点，结合规则生成备注、工单或审核任务

打标缺少业务现场

只看通话文本，不知道运单状态、客户偏好和网点入柜约束。

→ 通过 MCP 查询运单、轨迹、偏好与网点

标签结果无法解释

外部平台只返回 value，判错后难以定位原因。

→ 输出原文证据、判断原因、置信度并自动校验

低置信结果直接执行

语义混乱、系统音等结果仍可能触发默认动作，缺少审核与恢复。

→ 低置信转人工，工作流负责审核、重试与留痕

04 / MCP 工具与职责边界

模型提出请求，Java 完成动作

recognize_call_intent识别八类电联意图，返回证据、置信度、地点要素和审核标记
get_waybill_info查询产品标识、运单状态、收件小区和配送网点
get_tracking_info查询派件上车、电联等物流操作轨迹
get_customer_preference查询客户配送偏好、偏好地点和最近电联意图
get_station_info查询网点入柜配置、排除产品和配送约束

当前全部为只读工具。配送备注、异常工单和 CheckType 写操作不直接暴露，防止绕过人工审核门。

交给大模型

  • 理解非结构化通话文本
  • 识别意图，提取地点与时间
  • 根据上下文选择查询工具
  • 结合规则生成处置建议
  • 说明低置信或转人工原因

必须交给 Java

  • 参数、权限和运单状态校验
  • Racking 标签与 CheckType 映射
  • MCP 工具执行与异常处理
  • 审核门、幂等、重试和状态持久化
  • 备注、工单和 CheckType 最终写操作
